Fitted Labels vs. Proved Bounds

Six BigO(Bench) solutions modelled in Rocq with machine-checked cost bounds, compared against the label the benchmark fitted for each.

The question

BigO(Bench) labels 1.19M solutions by profiling them at varying input sizes and fitting a curve. The paper calls these “performance profiles and not theoretical complexities” — 92% time / 84% space agreement with human annotation.

You cannot verify a curve fit. You can model the solution, prove a bound, and see whether the label agrees.

The disagreements are the output.

Three to walk through

Suggested demo path. A finding that did not survive review, a precision failure that raises a design question, one clean case done twice in two different styles.

Cases

450_204 1421_C — Palindromifier Withdrawn
Python
print('3 L 2 R 2 R',len(input())*2-1)
What was claimed

Charging input() one tick per character gives cost = n, refuting the fitted O(1).

Rocq, after the fix
Theorem cost_palindromifier :
  forall s, cost (palindromifier s) = 0.

Theorem label_sound :
  BigO T (fun _ => 1).
Every program that reads its input is Ω(input size), so a proof whose whole cost is the read says nothing about the algorithm. Cost.v now fixes input and output as free; under it the fitted O(1) is correct. Replaced by 433_57.
5_100 622_A — Infinite Sequence Overstated
Python
n=int(input())
k=1
while(n>k):
   n-=k
   k+=1
print(n)
Cost model

One tick per iteration. Rocq needs structural recursion, so the loop takes fuel; run_finishes proves the fuel is never exhausted, so the bound is not truncation.

Rocq
Theorem iters_sqrt : forall n,
  iters n * (iters n + 1) <= 2 * n.

Theorem iters_exponential_in_bitlength :
  forall k, 1 <= k ->
  2 ^ k <= iters (2 ^ (2*k+2)).

Example iters_table :
  (iters 64, 256, 1024, 4096)
  = (10, 22, 44, 90).
Labelled O(n); the loop subtracts 1, 2, 3, … so it runs in ~√(2n). Both sizing conventions are proved. By value it beats O(n); by bit length it is not polynomial — 2k iterations on a (2k+3)-bit input. Which convention should the dataset use?
167_177 1184_A1 — Heidi Learns Hashing Overstated
Python
n = int(input())
x = math.floor(math.sqrt(n))
for i in range(1, x):
  if (n-1-i**2-i)%(2*i) == 0 :
    print(i, (n-1-i**2-i)//(2*i))
    break
Cost model

One tick per iteration. math.floor(math.sqrt(n)) is Nat.sqrt n exactly, so the loop bound is √n.

Rocq
Theorem T_upper : forall n,
  T n <= Nat.sqrt n.

Theorem fitted_label_not_tight :
  ~ BigOmega T (fun n => n).

Example T_10000 : T 10000 <= 99.
A second √n loop labelled O(n) — reached by an explicit math.sqrt where 5_100 sums 1+2+3+…, so two independent programs, not one bug twice. Two cases is a reason to measure, not a measurement.

Python
N = int(input())
A = [int(i) for i in input().split()]

Cost model

B is nat -> nat with pointwise update, not a Rocq list — Python list stores are O(1), and a list model would make this program look quadratic.

Rocq
Lemma T_eq : forall n, T n = n.

Theorem true_class : Theta T (fun n => n).

Theorem fitted_label_sound :
  BigO2 (fun n _ => T n)
        (fun n m => n + m).
Sound — O(n) sits inside O(n+m) — but there is one input size here, so the label's second parameter has nothing to track.

Python
n=int(input())

l.sort()
x=0

Cost model

One tick per element parsed, the sort from MergeSort.v, one tick per scan step.

Rocq
Theorem fitted_label_sound :
  BigO T (fun n => n * Nat.log2_up n).

Theorem lower_bound_is_only_linear :
  BigOmega T (fun n => n).
Upper bound transfers: Timsort is also O(n log n) worst case. The lower bound does not — Timsort is Θ(n) on sorted input, so Ω(n log n) would be a model artefact. Gap left open, not closed.
2389_139 ABC 044 — Beautiful Strings Tight
Python
s=input()
ch=0
for i in s:
  if s.count(i)%2 ==1:
    ch=1
print("YNeos"[ch::2])
Cost model

One tick per character compared by str.count, which scans the whole string. Cost is independent of contents.

Rocq
Theorem cost_beautiful : forall s,
  cost (beautiful s) = length s * length s.

Theorem fitted_label_is_tight :
  Theta T (fun n => n * n).
Exact, not merely bounded: the cost is n² on the nose, for every input.

Why the proofs mean something

  • One definition. M A pairs a value with a step count, so cost is a projection of the same term. A separate cost function could be fun _ => 0 and prove everything.
  • Adequacy required. fun l => ret l and fun _ => ret [] cost nothing and satisfy every upper bound — hence msort_perm, msort_sorted, run_finishes.
  • Disagreements are theorems (~ BigO, ~ BigOmega), not comments.
  • Sorting done once. All 127 O(nlogn) records call sort/sorted, so MergeSort.v unblocks the class.

Limits

No rate is claimed here. Six entries say nothing about the 640-record test set, and selection was not uniform over it. A start, not a sample.

  • The cost model is the whole attack surface: the monad makes cost match the model, nothing makes the model match Python.
  • 603_284 has an open gap (Ω(n) to O(n log n)); the Ω(n) comes from the pairwise scan, not from the input read.
  • Input and output are not charged. That convention is standard, and it decided 450_204 — see Cases.
  • Time test set only; space needs a high-water-mark measure.
  • No comparison against the framework's fitted coefficients.

Open questions

  • Measure the rate? ~30 entries would give a defensible number, at roughly a day of proof work per non-trivial case.
  • What should “n” mean? Settled as fact, open as choice — value-based follows the benchmark, bit-length follows the textbook and flips the verdict.
  • Are √n loops the blind spot? Both Overstated cases are √n loops over integer values. Testable against the framework directly, far cheaper than by proof.
  • How far to model the stdlib? Timsort already blocks one lower bound.
