Fitted Labels vs. Proved Bounds

Six solutions from BigO(Bench)'s time test set, modelled in Rocq and given machine-checked complexity bounds — then compared against the label the benchmark's dynamic inference framework fitted for each. One label is not an upper bound at all; two more are sound but overstate a √n loop as O(n).

What this is asking

BigO(Bench) labels 1,190,250 Code Contests solutions with time and space complexity classes, inferred by profiling each solution at a range of input sizes and fitting a curve. The paper is explicit that these are “statistically significant ground truth performance profiles and not theoretical complexities”, at 92% time / 84% space agreement with human annotation on a sampled subset.

So the question is not “can we verify their labels” — a curve fit is not the kind of thing that admits verification. It is:

Take a solution, model it in Rocq, prove a bound, and see whether the fitted label agrees.

The disagreements are the output. A pile of agreeing cases is not a finding.

Case by case

450_204 1421_C — Palindromifier NotUpperBound — the label is not an upper bound
Python source
print('3 L 2 R 2 R',len(input())*2-1)
Cost model

len on an existing Python str is O(1) and charged nothing. But input() must read the line: one tick per character. Nothing else depends on the input.

Rocq proves
Lemma T_eq : forall n, T n = n.

Theorem fitted_label_unsound :
  ~ BigO T (fun _ => 1).

Theorem true_class :
  Theta T (fun n => n).
Framework says O(1); the program is Θ(n). Not a loose bound — not an upper bound at all. Likely cause: the input expansion never scaled the single line this problem reads, so measured runtime looked flat.
5_100 622_A — Infinite Sequence Overstated — program is cheaper than the label
Python source
n=int(input())
k=1
while(n>k):
   n-=k
   k+=1
print(n)
Cost model

One tick per loop iteration; the body is O(1) arithmetic. Rocq needs structural recursion, so the loop takes a fuel parameter — and run_finishes proves that fuel is never exhausted, so the bound is not an artefact of truncating the loop.

Rocq proves
Theorem run_finishes :
  forall n, finished n = true.

Theorem iters_sqrt : forall n,
  iters n * (iters n + 1) <= 2 * n.

Theorem iters_lower : forall n j,
  j*j + 2*j + 1 < n -> j <= iters n.

Theorem iters_exponential_in_bitlength :
  forall k, 1 <= k ->
  2 ^ k <= iters (2 ^ (2*k+2)).

Theorem fitted_label_not_tight :
  ~ BigOmega iters (fun n => n).

Example iters_table :
  (iters 64, iters 256,
   iters 1024, iters 4096)
  = (10, 22, 44, 90).
Framework says O(n); the loop runs in ~√(2n). It subtracts 1, 2, 3, … so it halts after about √(2n) steps. At n = 5050 that is 99 iterations, not 5050 — checked by computation.

Both sizing conventions are now proved, not asserted. Here “n” is the integer's value, not a length. iters_sqrt gives ~√(2n) in the value; iters_exponential_in_bitlength gives at least 2k iterations on a (2k+3)-bit input. So under one convention the loop beats the fitted O(n), and under the other it is not polynomial at all. The conventions do not merely shift constants — they decide this record's verdict. Which one should the dataset use?
167_177 ★ 1184_A1 — Heidi Learns Hashing (Easy) · drawn at random Overstated — same failure, independent program
Python source
import math
n = int(input())
x = math.floor(math.sqrt(n))
p = 0
for i in range(1, x):
  if (n-1-i**2-i)%(2*i) == 0 :
    print(i, (n-1-i**2-i)//(2*i))
    p = 1
    break
if not p:
  print("NO")
Cost model

One tick per loop iteration. math.floor(math.sqrt(n)) is Nat.sqrt n in Rocq — exactly floor of the real root — so the loop bound is √n, not n.

Flagged, not modelled: i**2 and the % / // are O(1) only while values fit a machine word.

Rocq proves
Theorem T_upper : forall n,
  T n <= Nat.sqrt n.

Theorem fitted_label_sound :
  BigO T (fun n => n).

Theorem fitted_label_not_tight :
  ~ BigOmega T (fun n => n).

Example T_10000 : T 10000 <= 99.
A second √n loop labelled O(n) — and this one was drawn at random. It reaches √n by an explicit math.sqrt bound where 5_100 reaches it by summing 1+2+3+…, so these are two independent programs hitting the same blind spot, not one bug seen twice. At n = 10,000 the loop runs 99 times, not 10,000 — computed, and the bound is attained rather than merely available.

Two cases is still not evidence of a systematic gap. It is the reason to go and measure one.
1421_53 p02899 ABC 142 — Go to School SoundLoose — correct, but names a size parameter that isn't there
Python source
N = int(input())
A = [int(i) for i in input().split()]
B=[0]*N
for i in range(N):
  B[A[i]-1]=i+1
print(*B)
Cost model

One tick per element parsed, one per loop iteration. B is modelled as nat -> nat with pointwise update, not as a Rocq list — Python list stores are O(1), and a list model would make each store O(n) and “prove” this program quadratic.

Rocq proves
Lemma T_eq : forall n, T n = 2 * n.

Theorem true_class :
  Theta T (fun n => n).

Theorem fitted_label_sound :
  BigO2 (fun n _ => T n)
        (fun n m => n + m).

Theorem second_parameter_is_spurious :
  forall n m m', ...
O(n) is inside O(n+m), so the label is sound — but there is only one input size here, and the cost provably does not vary with the second parameter at all. That says something about how size variables are picked from the problem's dataclass, not about the program.
603_284 1041_A — Heist SoundUpperOnly — tightness deliberately not claimed
Python source
n=int(input())
l=list(map(int,input().split()))
l.sort()
x=0
for i in range(n-1):
    x+=l[i+1]-l[i]-1
print(x)
Cost model

One tick per element parsed; the sort as modelled in MergeSort.v; one tick per step of the pairwise scan (indexed access is O(1) in Python, so the scan is linear).

Rocq proves
Lemma T_upper : forall n,
  T n <= 2 * Nat.log2_up n * n + 2 * n.

Lemma T_lower : forall n, n <= T n.

Theorem fitted_label_sound :
  BigO T (fun n => n * Nat.log2_up n).

Theorem lower_bound_is_only_linear :
  BigOmega T (fun n => n).
The upper bound transfers; the lower bound would not. CPython's sort is Timsort, also O(n log n) worst case, so modelling it as merge sort does not understate. But Timsort is Θ(n) on already-sorted input where merge sort is not — so proving Ω(n log n) here would be an artefact of the model and false of the real program. Proved: Ω(n) ≤ cost ≤ O(n log n), with the gap left open and recorded as such rather than closed.
2389_139 p04012 ABC 044 — Beautiful Strings Tight — label is exactly right
Python source
s=input()
ch=0
for i in s:
  if s.count(i)%2 ==1:
    ch=1
print("YNeos"[ch::2])
Cost model

One tick per character compared by str.count, which scans the whole string; the outer for is charged only through the counts it triggers. Cost is independent of the string's contents, so the size-indexed family loses nothing.

Rocq proves
Theorem cost_beautiful : forall s,
  cost (beautiful s) = length s * length s.

Lemma T_eq : forall n, T n = n * n.

Theorem fitted_label_is_tight :
  Theta T (fun n => n * n).
Exact, not just bounded. The cost is n² on the nose, so the fitted label is not merely sound but tight.

How the proofs are kept honest

  • One definition, not two. M A pairs a value with a step count; the algorithm and its cost are the same term, cost being a projection. A separately-written cost function has nothing tying it to the algorithm — cost := fun _ => 0 would prove every bound.
  • Adequacy is required, not decoration. An upper bound on cost is vacuous if the function skips the work: both fun l => ret l and fun _ => ret [] cost nothing and satisfy every upper bound. So the sort carries msort_perm (nothing dropped) and msort_sorted (actually sorted), and the fuel-based loop carries run_finishes.
  • Disagreements are theorems. Both unsound verdicts are backed by a refutation (~ BigO, ~ BigOmega), not by a comment.
  • Sorting is done once. MergeSort.v proves O(n log n) by recursing on a depth with precondition length l <= 2 ^ d, so the recurrence closes by induction on the depth alone and the logarithm appears only at the top-level call. All 127 O(nlogn) records in the time test set call sort or sorted (measured), so this unblocks that whole class.

Limits — read before quoting any number

No rate is being claimed, and none should be read off this page. Five of the six were chosen as the shortest solution in their label class — a selection that skews heavily toward one-liners and I/O-bound code, plausibly exactly where the framework's input expansion does worst. One entry (167_177) is drawn at random; that is a start, not a sample. bench.py sample --seed 20260817 produces a reproducible draw when someone wants to measure this properly.

  • The cost model is the whole attack surface. The monad makes cost match the model; nothing makes the model match Python. Where the ticks go is a judgement call, stated in each file's header.
  • “Overstated” is not “wrong”. Only 450_204's label fails to bound the program. O(n) genuinely does bound a √n loop — it just says nothing useful. Four of the six labels are sound.
  • One case has an open gap (603_284: Ω(n) to O(n log n)), recorded rather than closed with a model artefact.
  • Two √n cases is suggestive, not systematic. They are independent programs, which is what makes it worth measuring — but two is not evidence of a pattern.
  • Time test set only. Space is untouched — the monad counts steps and would need a separate high-water-mark measure.
  • No contact with the framework's numbers. Each record carries a time_curve_coefficient and measured runtimes; relating a proved constant to a fitted coefficient has not been attempted.

Open questions for Thursday

  • Is the disagreement rate worth measuring properly? The seeded sampler is in place; a draw of ~30 across the 11 label classes would give a defensible number. Roughly a day of proof work per non-trivial case is the cost estimate to weigh against it. That is the difference between an anecdote and a result.
  • Are √n loops the blind spot? Both Overstated cases are √n-bounded loops on integer values. If the framework's input expansion scales a value linearly, a √n response curve is easy to read as linear. Cheap to test directly against the framework rather than by proof.
  • What should “n” mean? Now settled as a fact and open only as a choice: 5_100 carries theorems for both readings — ~√(2n) by value, ≥ 2k iterations on 2k+3 bits. Value-based sizing follows the benchmark's dataclass; bit-length follows the textbook and flips the verdict from “cheaper than labelled” to “not polynomial”. Which does the dataset want?
  • How far do we model the standard library? Timsort's adaptivity already blocks one lower bound. Modelling it faithfully is a project in itself.
  • Is “unsound label” the interesting finding, or is “spurious size parameter”? The latter (1421_53) may be systematic and cheaper to detect at scale.
